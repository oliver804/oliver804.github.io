Local Route Launcher

Starts a compatible ChatGPT desktop app with your own HTTP proxy, for that launch only. It does not provide a proxy, and it does not change the system proxy, DNS or routing.

Scope

What it does, and what it does not

It does

  • Save one HTTP proxy endpoint — address and port, no authentication — and reuse it on every launch.
  • Start a compatible Electron build of the ChatGPT desktop app with that endpoint passed as a Chromium launch argument and as proxy environment variables for its child processes.
  • Keep localhost off the proxy, so local tools keep working while the app is routed.
  • Offer start and graceful stop, three connection checks, a menu-bar or tray entry, light and dark appearance, and English/Chinese switching.

It does not

  • Provide a proxy, a tunnel or any network access. You need a local HTTP proxy that is already running and that you are allowed to use.
  • Change the system proxy, DNS settings, routing table or any other system-level network configuration.
  • Guarantee that every request from the app goes through the proxy. Voice, WebRTC and UDP traffic are not covered, QUIC is disabled so that HTTP requests stay observable, and child processes that ignore proxy environment variables will not follow.
  • Patch the application it launches. It passes arguments at launch; the app is free to ignore them, and its updates can change the behaviour this depends on.
  • Collect telemetry, ask for an account, or store settings anywhere except the local user profile.

Install

Once, then launch from here

macOS. Open the DMG and drag Local Route Launcher into Applications. The build is for Apple Silicon only.

Windows. Run the setup. It installs for the current user, needs no administrator rights, does not register a service and does not add itself to startup. The .NET runtime is bundled.

First run. Leave your proxy running, enter its address and port (for example 127.0.0.1 and 7890), save, quit any running copy of the app completely, then press Start. Use View proxy status to see what the checks observed.

After that. Open the app through the launcher, not from the Dock or the Start menu — settings are applied at launch, and a normal launch does not carry them. Closing the main window keeps the launcher in the menu bar or tray; quitting the launcher does not stop the app.

Walkthrough. The official site covers the same steps with an FAQ for the cases summarised here.

If the system blocks it

Neither build is signed by a paid certificate

macOS uses an ad-hoc signature and is not notarised, so Gatekeeper will refuse the first launch. After checking the file, allow it in System Settings → Privacy & Security. There is no need to disable SIP or any other system protection.

The Windows installer is not Authenticode-signed and may trigger SmartScreen. Compare the SHA-256 against SHA256SUMS.txt before running it. If your organisation blocks unsigned installers, that is a policy decision, not a bug to work around.

This is a real limitation rather than a badge. An unsigned build can be blocked, and the honest response is to document how to verify it, not to tell people to switch protections off.

Questions

Short answers

Does the launcher provide a proxy?
No. It passes the address of a local HTTP proxy you already run. It has no servers, no exit nodes and no network access of its own.
Will all traffic go through the proxy?
No, and the app does not claim it will. Chromium’s HTTP, HTTPS and WebSocket requests are covered and QUIC is disabled; voice, WebRTC and UDP are not. A child process that ignores the proxy environment variables will connect directly.
Why do I have to start the app from the launcher every time?
Because the setting is an argument passed at launch. Opening the app from the Dock or the Start menu starts it without that argument.
The app was not found. What now?
Only the Electron build of the ChatGPT desktop app is supported — not the older native app, and not a restricted Microsoft Store package that refuses to launch directly. Use the app picker to point at ChatGPT.exe if automatic discovery misses it.
Does it work on an Intel Mac, or on Windows ARM64?
No. macOS support is Apple Silicon only, and Windows support is x64 — ARM64 has not been verified, so it is not listed as supported.
Does it store anything about me?
The proxy address, port and interface language, in the local user profile. No account, no telemetry, no automatic upload. The connection check makes one HEAD request to chatgpt.com through your proxy, without account credentials.

Why it is built this way

Design notes

The problem

A desktop application that needs a proxy offers a choice that looks trivial and is not. You can set an HTTP proxy for the whole system, or you can take over routing with a TUN interface. Both are one switch. Neither tells you afterwards which requests actually used it.

System settings apply to every application on the machine, so unrelated tools begin failing through a path you configured for one of them. TUN reaches lower still: it does not need the app to cooperate, and in exchange nothing above it can observe what happened. When a request fails you are left with a switch that is either on or off, and no way to ask a narrower question.

The narrower question

The question I actually had was smaller: how do I launch this one application with this one setting, for this one run? Chromium accepts --proxy-server at launch and honours HTTP_PROXY, HTTPS_PROXY and ALL_PROXY for its child processes. Passing those at launch scopes the setting to that process tree instead of the machine.

Two consequences follow immediately, and both come from choosing the smaller door. Localhost stays off the proxy, because local tools should keep working while the app is routed. And an argument is a request, not a policy — the application is free to ignore it, and some of its children do.

What the narrow door costs

  • The launch path becomes yours. Settings apply at launch; opening the app from the Dock or the Start menu will not carry them. The interface says so instead of hiding it.
  • Environment variables do not bind every child. Voice, WebRTC and UDP traffic may behave differently, and QUIC is disabled so that requests stay visible to the proxy.
  • The target can move. An Electron update can change the behaviour this depends on, and no contract says otherwise.
  • Two platforms, two launch mechanisms. Chromium behaves the same on both; Launch Services and Windows process creation do not.

Diagnostics that do not overclaim

A check is only useful if the failure it reports is real. The app runs three, and none of them is allowed to say more than it saw.

  • Proxy connectivity — a CONNECT tunnel was established and a TLS response came back through the configured proxy. An HTTP 403 at this stage is a response, not proof that a chat session works.
  • Launch arguments — the running main process carries proxy arguments matching the saved settings. This is the only check that answers the question directly.
  • Observed connections — a TCP snapshot at one moment. The absence of a connection is not proof of direct access, and a hostname cannot be matched against a numeric address in the snapshot.

Each limitation is printed beside the tick, not in a footnote. A diagnostic that says “connected” when it means “something responded” is worse than no diagnostic at all, because it ends the investigation.

The other half is packaging

Shipping was the part I underestimated. The build takes its version from a single file, maps compiler paths so local directory names never end up inside the binary, and will not publish a release until both platform builds have passed.

Neither build carries a paid signing certificate. macOS uses an ad-hoc signature, Windows ships unsigned, and both facts sit next to the checksums rather than in a footnote. That is a real limitation: the download can be blocked by the operating system, and the honest response is to document verification instead of telling people to switch security features off.

What changed between releases

1.0.0 was the first public release: per-launch proxy settings, start and stop, menu bar, light and dark. 1.1.0 renamed the application to Local Route Launcher while keeping the repository URL and saved preferences compatible, and made language switching immediate and persistent. 1.2.0 added the Windows edition and made release publication wait for both platforms. None of that is what users ask for, and all of it decides whether the tool feels finished.

The tool is deliberately small. That is the only reason it can be explained on one page — and the only reason its limits can be listed without a disclaimer section.
