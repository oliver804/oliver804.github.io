About

Writing something down is the fastest way to find out whether it holds. This site is where that happens — much more often for projects than for prose.

Most of what I learn while building software disappears within a month. The decision that took an afternoon, the reason a simpler approach failed, the check that turned out to catch the problem — all of it ends up in a closed tab or a commit message nobody reads twice. This site is the storage.

It is not a portfolio in the sense of a folder of screenshots. The site has three parts that feed each other: the project itself, the writing that came out of building it, and a short list of facts about both. The project is documented with its limits rather than its highlights. When the list grows, it will be because more things were finished, not because the page needed filling.

What I work on

Java, data, front end

Most of my work sits in the unglamorous middle of software. Java services and the integration between them; data pipelines and the modelling that keeps the numbers usable months later; React interfaces when something has to become a screen and no one else is going to build it.

The connecting thread is not a language or a framework. It is what happens after delivery: whether the system can still be understood by the person who operates it next, and whether the data coming out of it can still be trusted when a source changes shape without telling anyone.

How I work

Small changes, written limits

I try to start from a specific annoyance rather than a technology. Projects that begin with “I want to try this tool” tend to end as demos; projects that begin with “this takes four steps and should take one” tend to end as something still in use a year later. Local Route Launcher started as the second kind.

I prefer the smallest change that answers the actual question, and I try to write the limitation down at the same moment as the feature. The two are much easier to remember together than apart.

On AI-assisted development

Review, not generation

I use coding agents as part of the work, and I am careful about what that means in practice. They are good at producing a first version of something reviewable. They are bad at knowing when that first version is subtly wrong, and confident in proportion to how wrong it is.

So the interesting question is not what a model can generate. It is what the review step has to become: can the change be read by someone who did not write it, can the failure be reproduced, and does the test fail when the fix is removed. That is the part I am trying to get better at, and it is why some notes here are about process rather than code.

Why this page rarely changes

And why that is the design

I am not a blogger, and the site is not arranged as one. There is no archive to keep current, no weekly thing, no “latest” rail that quietly turns into a stale date. What changes is the work list: a version number, a new screenshot, a project that finishes. Those changes are honest and infrequent, and the layout is built to survive them rather than to demand them.

Notes appear when a build produces a decision worth recording — currently four per project, in one burst. Between projects the site is quiet, and the date in the footer says exactly how long it has been quiet.

Colophon

No build step, by choice

Hand-written HTML and one stylesheet. No framework, no build step. Apart from the two analytics tags described at the end of this page, nothing is requested from another domain — the typeface is served from here. Body text is set in the system sans; headings and figure captions in Newsreader; version numbers, dates and paths in the system mono.

Hosted on GitHub Pages, published from the main branch. The source is public if you want to see how little there is: oliver804/oliver804.github.io. A page here is one file; adding a note means editing HTML by hand, which is also a useful filter on how many notes get written.

Analytics

Two tags, added later

Two analytics scripts run on every page: Google Analytics 4 and Microsoft Clarity. The reason is narrow — whether anything here is read, which pages are found, and where visits stop. There is no advertising, no remarketing, and no profile of you assembled across other sites.

Both are third-party scripts, loaded from googletagmanager.com and clarity.ms. Both set first-party cookies and report page views, referrers and device type. Clarity additionally records interaction data: clicks, scroll depth, and session recordings under its default masking. Blocking either one changes nothing about how a page renders — this is static HTML that never waits for a script to arrive.

This is a reversal. An earlier version of this page said the site carried no analytics and made no third-party requests, and that was true when it was written. It is recorded here instead of being quietly deleted, because the claim was specific enough that someone may have believed it.
